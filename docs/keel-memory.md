# Keel 内存排查

2026-10-14 的客户端采样确认，OneCatch 高内存不只来自对话文档。运行中的 `v0.2.3` 客户端物理占用为 876.2 MiB，峰值 954.2 MiB；稍后的采样为 954.8 MiB、峰值约 1 GiB。采样期间有任务运行，未做相同内容的空闲对照，不能据此判断内存泄漏。

## 客户端证据

通过 `go version -m` 确认被测客户端依赖 `github.com/dyike/keel v0.2.3`。`vmmap -summary` 的首次采样如下：

| 分类 | 驻留/脏内存 | 说明 |
| --- | ---: | --- |
| IOSurface | 165.8 MiB | 三个 5016×2820 的 CAMetalLayer Display Drawable，各约 55.3 MiB |
| owned unmapped (graphics) | 358.6 MiB | 图形资源；尚未归因到具体纹理、图集或渲染目标 |
| IOAccelerator (graphics) | 55.2 MiB | 图形驱动资源 |
| Untagged | 驻留 289.5 MiB，脏 205.8 MiB | 不能直接当作 Go 活跃堆，仍需堆采样区分 |
| CG Image | 32.0 MiB | 系统图像分配；尚未定位到具体图片 |

前三类合计约 579.6 MiB。物理占用、RSS、虚拟地址空间和各分类总和口径不同，不可直接互换。`ps` 的 RSS 比活动监视器低，不能据此认为用户观察有误。

Keel 已有空闲回收逻辑：`gio/gpu/gpu.go` 的 `Idle` 标记覆盖纹理可回收；`Trim` 释放可重建纹理和帧缓冲；`gio/app/metal_idle_macos.go` 在持续一秒没有绘制后收缩 drawable。当前采样存在绘制活动，不是持续空闲回收后的内存下限。

## 主分支升级与实测

仓库依赖已从 `v0.2.3` 固定到主分支提交 `74ea9c578ec76b09d2b74a853c6b28b4d0d8dc81`，Go 伪版本为 `v0.2.4-0.20261014021630-74ea9c578ec7`，不依赖浮动的 `main` 或本地 `replace`。

其中 `34b9283` 减少每帧分配：普通元素按需创建编辑器、缓存节点按需分配布局记录、布局使用栈上临时数组、状态键避免拼接字符串。该提交没有修改 GPU 资源管理，因此不能把以下分配量下降解释成进程总内存同比下降。

Apple M5 Pro、2× 布局下，每场景固定 200 次、运行两遍，取 B/op 的算术平均：

| 场景 | 升级前 B/op | 升级后 B/op | 减少 |
| --- | ---: | ---: | ---: |
| 普通多消息滚动 | 945,249 | 835,347 | 11.6% |
| 长回复滚动 | 2,356,102 | 2,084,332 | 11.5% |
| 静态对话帧 | 747,065 | 650,036 | 13.0% |
| 30 个增量合批 | 1,833,088 | 1,746,184 | 4.7% |

这些基准运行布局和输入路由，不包含窗口 GPU 呈现；B/op 是累计分配速率，不是常驻内存。静态帧的分配次数从 4,670 降到 3,642，长回复从约 26,820 降到 15,949。测试期间有其他任务运行，不使用耗时差异推断帧率收益。

复测命令：

```sh
go test ./internal/app/keel -run '^$' -bench 'BenchmarkConversation(IdleFrame|StreamBurst|Scroll)$' -benchtime=200x -benchmem -count=2
go test ./internal/app/keel ./cmd/app -count=1
go vet ./internal/app/keel ./cmd/app
go build -o /tmp/onecatch-memory-updated ./cmd/app
```

升级后的界面包与入口包测试、`go vet` 和 macOS 构建均通过，包括复制选区、图片粘贴后的中文输入和托盘业务回归。

尚未替换用户正在运行的客户端，不能报告升级后真实客户端物理占用下降。后续应在相同窗口大小、同一任务内容下对比旧版与新版的运行、空闲和滚动状态，并采集 Go 活跃堆；剩余图形资源需要进一步定位，不能仅通过限制 Go 堆解决。

## 底层纹理修复

进一步复现发现两条放大路径：整帧只要存在透明度图层，就会禁用所有文字的着色纹理共享；圆角路径裁剪或透明度图层内的文字会按颜色复制整张 1024×1024 字形图集，每份 4 MiB，即使只画几个字。

Keel 改为按绘制操作判断透明度图层归属，保留图层外文字共享；CoreText 图集改为 256×256，每份颜色副本缩至 256 KiB，页面上限从 8 增至 128，保留 32 MiB 的像素预算。未改变字形光栅化或窗口三缓冲。三块 5016×2820 drawable 属于同一个窗口，各约 55.3 MiB；保留三个是为了避免缩放时 Core Animation 持有旧表面导致主线程等待，不能解释成三个窗口。

使用 `TestConversationMemoryProfile` 在原生 Metal 离屏窗口绘制相同的 OneCatch 长回复，尺寸为 5016×2820、2× 缩放。每次启动新进程，绘制 12 帧后 GC，再用 vmmap 采样；截图读回放在采样之后。升级到主分支但未应用底层修复的版本，与修复版本交替运行三轮：

| 版本 | 三次物理占用（MiB） | 中位数（MiB） |
| --- | --- | ---: |
| 主分支基线 | 474.8 / 478.6 / 463.5 | 474.8 |
| 底层修复 | 362.1 / 370.4 / 335.5 | 362.1 |

中位数减少 112.7 MiB（23.7%）。离屏复现不包含真实窗口的 drawable 池，也不包含运行任务的全部历史数据，不能替代原客户端前后对照。截图对比有 10,936 个像素出现差异，单通道最大差值为 1/255，与共享着色路径的舍入差异一致。

复测命令（每次使用不同输出目录，并在新进程中运行）：

```sh
ONECATCH_MEMORY_PROFILE=/tmp/onecatch-memory-profile go test ./internal/app/keel -run '^TestConversationMemoryProfile$' -count=1 -v
```

输出 `vmmap.txt`、`heap.pprof` 和 `frame.png`。默认测试跳过该诊断，避免常规测试启动 GPU 采样。底层补丁已通过 [Keel PR #23](https://github.com/dyike/keel/pull/23) 合入，并发布为 [v0.2.4](https://github.com/dyike/keel/releases/tag/v0.2.4)。OneCatch 固定依赖 `v0.2.4`，移除本次排查创建的本地 `go.work`，构建不再依赖相邻源码目录。发布说明记录了主分支已有的 Windows 菜单位图测试失败；这次修复未涉及该路径。

## 2026-10-14 真实客户端继续归因与安装验证

本轮最终安装版使用用户真实数据目录，在 5016×2820 窗口打开“梳理 akx 的功能与架构”：静止物理占用 157 MiB，往返滚动三屏后静止为 149 MiB；Go 活跃堆 32.68 MiB、堆使用页 42.66 MiB。静止占用低于 200M，加载和滚动峰值仍超标，不能宣称全程低于 200M。此前原进程约 934.5 MiB 的采样包含运行任务，本轮最终打开的是已完成对话，因此不是严格相同执行状态的百分比对照。

采样使用 `footprint` 与 `vmmap -summary` 的物理占用口径，没有以 RSS、虚拟地址或手动 GC 后的单点值代替。最终堆快照未设置 `gc=1`。真实窗口截图确认内容存在，完成上下滚动；没有发送测试消息或启动任务。

### 归因与改动

- 运行状态灯调用持续动画，使整窗 GPU 绘制持续发生；改为静态绿点，状态变化仍更新。
- 项目工作流每两秒检查一次，无变化仍调用 `core.Update`，整窗重绘并推迟两秒空闲堆回收。Keel 增加 `core.UpdateIf`：驻留后台在同一帧锁内检查，仅在返回 true 时请求绘制、更新回收活动时间。工作流签名和 Git 快照不变时不重绘。
- macOS 打包应用已经有 Dock 图标，再调用 `SetIcon` 额外保留约 32 MiB 的 CG Image。打包路径且图标文件存在时跳过重复设置；托盘和窗内 22dp 标志保留 96px 图片，开发运行仍设置 Dock 图标。
- 字体解析长期保留所有 TrueType 轮廓，堆采样中仅轮廓解析约 25 MiB。保留字形头和变体点数，完整轮廓在实际使用时解析并缓存；缓存共享加锁，Face 临时状态独立。验证副本活跃堆从约 63 MiB 降至约 33 MiB。同文件同 TTC 索引的命名实例共享只读字体表，实例身份仍独立。
- 帧缓冲的浪费比例写反，缩小场景时无法回收大缓冲；改为保留面积除以请求面积。
- 默认 Go 软内存预算为 96 MiB；显式 `GOMEMLIMIT` 优先。这个预算不包含 GPU 和原生内存，不等于进程总上限。

最终静止采样的主要类别：

| 类别 | 占用 | 已确认的含义 |
| --- | ---: | --- |
| Untagged | 约 56 MiB | 包含 Go 堆/运行时页，活跃堆约 32.7 MiB；不可把整类都当活对象 |
| IOSurface | 约 55.3 MiB | 当前显示的一块 5016×2820 drawable；活动时恢复三缓冲 |
| Malloc Small | 约 18 MiB | 原生堆，尚未逐对象完成符号归因 |
| owned unmapped (graphics) | 约 7.7 MiB | 空闲回收后残留驱动图形资源；先前 4 MiB 块的具体驱动对象尚未完全确认 |
| IOAccelerator (graphics) | 约 1.2 MiB | 图形驱动映射 |

纹理追踪已确认活动绘制的覆盖缓冲、256px 字形图集副本和上传缓冲；临时 Metal 日志代码已移除。没有把尚未确认的驱动内存统一称为“纹理泄漏”。

## 2026-10-14 加载和滚动峰值复测

用户将目标放宽为尽量低于 300M，仍要求不降低清晰度、不牺牲流畅度。本轮没有达到该峰值目标。最终无临时日志版本的真实窗口副本，在 5016×2820 尺寸打开同一长对话、往返滚动三屏四轮后：静止 164.8 MiB，进程峰值 520.6 MiB，250ms 采样捕获最高 519 MiB。空白首页启动本身也曾达到 394.4 MiB，不能把全部峰值归到长对话数据。

### 保留的优化与验证

Metal 批量绘制增加路径覆盖纹理，允许圆角裁剪内的着色字形共享图集，减少逐字绘制和按颜色复制图集。圆角矩形另携带保守内区：只有所有路径祖先完整包含绘制像素边界时才跳过覆盖合成，留出一像素抗锯齿余量；边缘、未知路径、描边、旋转等情况保留原路径。透明度图层仍使用原回退路径。

固定离屏对话的 5016×2820 像素对照最大单通道差值为 1/255，无更大差异。新增回归覆盖纹理槽耗尽、绘制顺序、着色、分配失败回退、圆角边缘、嵌套路径和变换；原生 Metal 像素测试验证十组圆角/交集裁剪和图集着色。Gio、typesetting 全套测试及 OneCatch 界面/入口测试通过，OneCatch 对应 `go vet` 通过。

真实窗口副本使用同一数据副本和侧栏点击入口，两个带临时计时日志的进程分别执行四轮三屏往返滚动：

| 指标 | 本轮改动前 | 保留优化后 |
| --- | ---: | ---: |
| 加载完成时已记录的进程峰值 | 502 MiB | 488 MiB |
| 滚动期间采样最大值 | 530 MiB | 512 MiB |
| 滚动结束时进程累计峰值 | 536 MiB | 519 MiB |
| 全过程帧提交耗时 P50 | 3.17 ms | 3.06 ms |
| 全过程帧提交耗时 P95 | 30.84 ms | 8.15 ms |
| 最慢单帧 | 135.35 ms | 289.78 ms |

这是各一次交互对照，帧数分别为 61 和 118；输入惯性、布局收敛和系统负载存在差异，不据此宣称稳定百分比收益。计时覆盖布局到 `e.Frame` 提交，不包含完整显示链路，不能换算实际帧率。优化版最慢帧出现在首次启动，首帧尖峰仍未消除。另一次缩小到 2240×1520 后滚动、再恢复 5016×2820，窗口继续响应并呈现内容，但累计峰值升至 600.4 MiB；缩放峰值也不能算达标。缩小后的较低内存不能用于替代原尺寸结果。

最终版本已移除临时帧计时和纹理分配日志。该版本再次在真实窗口副本验证，结果见本节首段。当前 `/Applications/OneCatch Keel.app` 正在执行用户任务，本轮未重启或替换它；该进程仍运行上一轮优化版。候选二进制保存在 `/tmp/onecatch-peak-investigation/final`，不能把副本结果描述成主客户端已升级后的结果。

### 剩余占用与撤回的实验

最终 519 MiB 样本中，主要分类为图形未映射物理内存 210 MiB、IOSurface 166 MiB、Untagged 83 MiB、原生小分配 18 MiB、IOAccelerator 图形映射 18 MiB、其他未映射物理内存 14 MiB。静止后 Go 活跃堆约 33.8 MiB、堆使用页约 44.9 MiB；采样没有强制 GC。Untagged 仍不能整体当作活对象，图形未映射内存也尚未逐项归因到驱动对象。

原生纹理追踪看到滚动中约 1932×5295 的 R16Float 覆盖缓冲和 256×256 字形图集；这些是已确认的应用资源，不能据此解释全部 210 MiB 驱动占用。统一上传 uniform、采样纹理改共享存储、限制命令队列未完成缓冲数量，以及 32/64 MiB Metal 纹理堆实验，均未显示稳定的总占用收益，已撤回。纹理堆试验按 Apple 文档启用 hazard tracking，最终源码不保留这条实验路径。参考：[Metal memory heaps](https://developer.apple.com/documentation/metal/memory-heaps)。

证据目录 `/tmp/onecatch-peak-investigation` 保存各轮采样和截图；最终证据在 `final-profile`，包括 `blank-vmmap.txt`、`idle-vmmap.txt`、`scroll-breakdown.txt`、`peak-breakdown.txt`、`stats-idle.json`、`heap.pprof`、`window.jpg`。本轮底层补丁仍依赖本地 `go.work`，尚未发布。
